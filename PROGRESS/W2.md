**认知更新(用户明确要求记入)**
- 学习项目要走**工程化写法**,不是"能跑就行"。AI 助手此前建议手动注册(30 行 Map.put,理由"30 个命令不值得上自动发现")被用户否决:这是学习项目,工程化模式本身是学习目标。修正 AI 的过度简化倾向。

**设计决策:命令分发用类路径扫描**
- 三方案对比:手动注册 / 反射+注解扫描 / Java SPI
- 选**反射+注解+类路径扫描**:加命令只写一个类贴 `@CommandName`,不用改注册代码;SPI 对 30 命令杀鸡用牛刀,手动注册不够工程化
- 面试可讲:"类似 Spring ComponentScan 的精简版,自己写 60 行扫描器处理 file/jar 双协议"

**概念学习(AI 讲解,用户逐段拆解理解)**
- 单例模式:private 构造 + static INSTANCE + getInstance();扫描填充只发生一次,触发点=第一个连接 `new CommandHandler()` 时的 `getInstance()`
- 注解机制:`@interface` 定义便利贴 / `@Retention(RUNTIME)` 决定活到运行时 / `@Target(TYPE)` 限定贴类 / `getAnnotation` 反射读取;`@Retention(RUNTIME)` 是扫描能成立的命门
- 类路径扫描三步:找位置(`getResources`) -> 列类名(file/jar 分支) -> 查注册(三道闸门 + 反射实例化)
- `Class.forName(name, false, loader)` 的 false:不触发类初始化,避免 Dispatcher 构造时扫到自身递归

**编码(AI 辅助搭框架,用户 review + 逐段拆解)**
- core 存储层:
  - `RedisDb` 单例,`ConcurrentHashMap<String, RedisObject>`(注:String key,二进制安全留 TODO)
  - `RedisObject` 抽象基类(区别于 `resp.RespObject`)+ `RedisString` + `RedisHash`
- command 命令层:
  - `Command` 接口:`execute(RedisDb, RespArray) -> RespObject`,`args[0]`=命令名
  - `@CommandName` 注解(`@Retention RUNTIME` + `@Target TYPE`)
  - `ClassPathScanner` 扫描器:file 协议递归目录 + jar 协议遍历条目,三道闸门过滤(接口/抽象类、有无注解、是否实现 Command)
  - `CommandDispatcher` 单例:构造时 scan 填充 map,`dispatch()` 做协议守卫 + 查表 + 调 execute + 兜底异常
  - 迁移 PING/ECHO/COMMAND 三命令到新框架
- handler 改造:`CommandHandler` 的 switch 删掉,改成 `dispatcher.dispatch(msg)` 一行
